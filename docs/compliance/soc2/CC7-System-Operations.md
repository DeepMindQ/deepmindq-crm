## Change Management Process

DeepMindQ implements a fully automated CI/CD pipeline with human approval gates. All changes to production follow this workflow:

### CI/CD Pipeline (`.github/workflows/ci.yml`)

**Blocking gates (must pass for merge):**
1. `security-gate` — Static security pattern scanning (grep-based)
2. `dependency-audit` — `npm audit` vulnerability scanning
3. `api-security-contract` — Auth guard verification on all API routes
4. `lint-and-typecheck` — ESLint + TypeScript strict mode
5. `test-unit` — Pure logic unit tests
6. `test-security` — Auth/CSRF/RBAC security tests
7. `test-api` — API route handler tests
8. `test-database` — Database/Prisma integration tests
9. `test-integration` — Cross-module integration tests
10. `test-m5-intelligence` — Trust and intelligence engine tests
11. `build` — Full production build verification

**Non-blocking (informational, allowed to fail):**
- `test-ai`, `test-ai-governance`, `test-ai-retrieval`, `test-ai-framework`, `test-ai-inference`
- `test-e2e`, `test-performance`, `test-ui`, `test-playwright`
- `infra-validation` — Terraform validation for infrastructure changes

### Production Deployment Pipeline (`.github/workflows/deploy-production.yml`)

9-stage gated pipeline triggered on push to `main`:
1. **CI Gate** — Awaits CI workflow completion
2. **Human Approval** — GitHub environment protection requires reviewer approval
3. **Build** — Production build with all secrets
4. **Backup** — Pre-migration backup if migrations pending
5. **Migration** — Prisma migrate deploy with P3005 drift handling
6. **Deploy** — Vercel production deploy (captures rollback ID)
7. **Smoke Tests** — Run against production URL
8. **Health Check** — 3-retry health endpoint validation
9. **Rollback** — Automatic rollback on health/smoke failure

**Evidence:** GitHub Actions logs at `https://github.com/<org>/deepmindq/actions`

## Monitoring and Alerting

### Application Monitoring

| Layer | Tool | Purpose | Configuration |
|-------|------|---------|---------------|
| Error tracking | Sentry | Runtime errors, unhandled exceptions | `sentry.client.config.ts`, `sentry.edge.config.ts` |
| Performance | Vercel Analytics | Response times, cold starts | Vercel dashboard |
| Uptime | `/api/health` endpoint | Liveness probe | `src/app/api/health/route.ts` |
| Cron monitoring | Vercel Cron logs | Job execution status | `vercel.json` (5 cron jobs) |

### Database Monitoring

| Metric | Source | Alert |
|--------|--------|-------|
| Connection pool usage | Neon console | >80% triggers Slack warning |
| Query performance | Neon console | >500ms p99 triggers investigation |
| Storage growth | Neon console | >80% capacity triggers alert |
| Replication lag | Neon console | Any lag triggers PagerDuty |

### AI Pipeline Monitoring

The intelligence pipeline (`src/app/api/ai/`) tracks:
- Provider response times and error rates
- Confidence score distributions
- Hallucination prevention guard triggers
- Evidence pipeline throughput

Evidence: `tests/ai/ai-governance-certification.test.ts`, `tests/ai/hallucination-prevention-certification.test.ts`

## Incident Response Procedures

Reference: `docs/incident-response.md`

Quick reference:
- **Detection:** Automated via Sentry, health check, and cron monitoring
- **Escalation:** PagerDuty → Slack `#incidents` → On-call engineer
- **Response:** Follow severity-specific runbook (RB-001 through RB-010)
- **Resolution:** Post-mortem within 48 hours (see RB-010 for template)

### Environment Management

| Environment | Purpose | Access | Data |
|-------------|---------|--------|------|
| **Production** (`main`) | Customer-facing | Admin + engineering (via PR) | Real data |
| **Staging** (`develop`) | Pre-release validation | All engineers | Synthetically seeded |
| **CI/CD** (ephemeral) | Automated testing | GitHub Actions only | Test fixtures |
| **DR Test** (on-demand) | Monthly backup verification | GitHub Actions only | Restored from backup |

**Environment protection:** Production and staging deployments use GitHub environment protection rules requiring human approval. Environment-specific secrets are isolated — CI uses fallback values (see `.github/workflows/ci.yml`, build job).
